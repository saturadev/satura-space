Unity for the web

Unity's Web platform builds a page with the game as WebAssembly. These are the settings and habits that decide whether a build loads everywhere and loads fast.

Building

  • The Web build support module has to be installed for the project's Unity version, through Unity Hub.
  • Switching the project to the Web platform reimports assets for it. On a large project that takes a while, and switching back does it again. Build when you mean to.
  • Build into a folder outside Assets/, for example Builds/Web/, and keep it out of git.
  • A WebGL template decides the index.html around the game. Platform SDKs often ship their own template; select it in Player Settings → Resolution and Presentation.

Compression

Unity can compress the build with Brotli or Gzip, or not at all. A compressed build needs the server to send matching Content-Encoding headers. Where you don't control the server, you have two choices:

  • Decompression Fallback on: the loader decompresses in the browser. Works on any host, starts a little slower.
  • Compression off: some portals ask for this and compress files themselves. Read the platform's Unity page.

On your own host, set the headers instead. Unity's manual has server configuration examples.

Size and loading

  • Most players leave a game that takes long to load, and portals measure it. Keep the first download small.
  • Strip engine code, use a high managed stripping level if the game still runs, drop unused packages and modules.
  • Compress textures, keep audio mono where it doesn't matter, avoid huge single assets.
  • Load later content on demand (Addressables or asset bundles) when the game is big.
  • Some hosts limit the size of a single file or the number of files. Unity's .data file is usually the largest.

In the browser

  • Audio can only start after the player's first tap or click. Make the first input start the sound.
  • Phones have far less memory than desktops. Test on a real phone, iPhones especially.
  • Use only relative paths to files in the build.
  • Wrap local saving in error handling: private browsing can block storage, and the game must keep working.
  • Decide mobile controls from the platform's device info where it gives one, not from touch support: many laptops have touch screens.
